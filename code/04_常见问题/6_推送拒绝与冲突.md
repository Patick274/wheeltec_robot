# 问题 6：fetch first / non-fast-forward / 冲突

本次真实问题包括独立历史、add/add 冲突和重建远程后残留的本地合并状态，
先看 [实际问题与处理](13_本次实际问题与处理.md)。普通分叉优先参考 [问题 7 的 merge 路线](7_两台电脑都提交了.md)；
下文 rebase 仅在尚未发布本地提交等前提满足时使用。

原因：远程存在本地没有的提交，可能另一台电脑推送了代码，或网页增加了 README。
先查看状态并保留自己的修改，不使用 git push -f、reset --hard 或删除 .git 来碰运气。

情况 A：两边有共同历史，自己的新增提交尚未发布
确保工作区干净，且当前在目标分支（本例 main）：
```powershell
git fetch origin
git log --oneline --graph --decorate --all -15
# 看清本地、远程进度。
git pull --rebase origin main
# 只在理解当前分支的前提下执行；把本地尚未发布的提交重放到远程之后。
```
遇到冲突时，打开冲突文件，人工整理 <<<<<<<、=======、>>>>>>> 包围的内容，去掉标记并保存。
```powershell
git status
git add -- '实际冲突文件路径'
# 每个已解决的文件都要添加。
git rebase --continue
# 可能出现多轮冲突，逐轮处理；编辑器打开时保存提交信息并退出。
```
完成后运行项目自己的检查，再 git push origin main。
如果不想继续本次 rebase：git rebase --abort，回到开始前的状态。
如果本地提交已经被别人使用，优先协调后 merge，避免随意 rebase 已共享历史：
工作区干净时 git fetch origin，再 git merge origin/main，解决冲突后提交并 push。

情况 B：本地修改还没提交，拉取会覆盖
```powershell
git stash push -u -m "同步前临时保存"
# -u 包括未跟踪文件，不包括被忽略文件；stash 仅保存在本机，不会上传。
git pull --ff-only
# 若分支已分叉，此处会停止，应先解决分叉再恢复修改。
git stash list
git stash apply 'stash@{0}'
# 核对要恢复的记录；apply 保留 stash，恢复可能仍有冲突。
```
恢复后确认文件完整、冲突已解决且内容已提交或另有可靠备份，再按需 git stash drop 'stash@{0}'。
不要在 pull 失败后继续机械粘贴命令。

情况 C：本地和远程独立初始化，没有共同祖先
对新手推荐：保留原目录作备份，clone 远程到一个新的目录；把自己的项目文件复制进去，
但不复制 .git；比较并保留远程 README 等有用内容，再 add、commit、push。
需要保留两套独立提交历史的进阶用户，先备份并核对仓库，再评估
git merge origin/main --allow-unrelated-histories；它是合并选项，不是日常 pull 的默认补丁。

其他推送拒绝：Authentication failed、Permission denied (publickey)、Repository not found、
受保护分支要求 PR、推送保护检测到凭据、大文件限制等，不由上述同步命令自动修好。
根据提示检查权限、认证、文件及规则；泄露的凭据先撤销，不要仅删除最新文件就认为历史里已清除。
