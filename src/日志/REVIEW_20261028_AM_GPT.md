## 3. 已查明：故障码必须更正

依据 FD1X5 手册第 7.12 节，印刷页 108-109：

| 读数 | 正确含义 | 不应继续采用的解释 |
|---|---|---|
| 0x2601:00 = 0x0001 | 错误状态 bit0：扩展错误 | 单凭该值认定为节点保护超时 |
| 0x2602:00 = 0x1000 | 错误状态 2 bit12：CAN 总线中断 | 将此字段解释为 CiA301 通用 EMCY 错误码 |

两个对象都是 Unsigned16 位掩码。0x2602 的 bit1 才是表中“看门狗”，不能和 bit12 混同。

因此，10.27 出现的这组数值应记录为“扩展错误伴 CAN 总线中断”。时间上与通信中断相邻是线索，但还不能区分适配器/线缆/供电、控制器 bus-off、主站退出或通信监督触发等具体原因。

“复位后能清除”只说明当时复位成功，不能据此认定原因已消除或允许自动恢复旧运动任务。

建议现场采集同一时间轴上的：

- 2601、2602、6041、6060/6061、6063、606C、60FD；
- 主站异常堆栈、最后有效目标与最后节点保护收发时间；
- can0 状态、CAN 错误计数、适配器和供电上下文。

1001、1003 可作为补充只读诊断，但需要先核对该驱动器固件的支持、数据宽度与子索引。1003 先读 sub0 是合理的；对象本身不支持时仍可能 SDO abort。当前 SDO 客户端遇到 abort 会使会话失效，因此这些可选探测应在独立、无运动会话中完成，不能混入活动控制循环或静默重连。

## 4. 仍需解决的关键问题

### 4.1 atexit 不是所有退出方式的停机保证

Python 官方文档明确说明：未被 Python 处理的信号、致命内部错误、os._exit() 不执行 atexit。SIGKILL、系统断电或 CAN 物理断链也不能依靠退出函数发出有效停车指令。

所以“异常退出时还有一次写入机会”可以成立；“任何崩溃都能立即停止”不能成立。日志中的 kill 节点测试必须明确具体退出方式，普通异常、SIGTERM 和 SIGKILL 应分开验收。

建议方案：

1. 主入口明确持有控制对象，用 try/finally 覆盖可处理退出；与 rospy.on_shutdown 共用幂等、限时的清理入口，atexit 作为最后补充。
2. 不让清理异常覆盖原始异常；记录停止帧是否尝试、是否收到回执、是否反馈停稳，失联时明确标记“停止未确认”。
3. 已关闭资源的 closed 标志只表示生命周期状态，不能被当作“电机已停稳”的证明。
4. 无法运行清理代码时，由驱动器自身通信监督及独立机械保持提供保护；需验证其已启用且动作符合该垂直轴需求。

节点保护 200ms × 3 是名义配置，不是已实测的端到端停止时间。不要把它写成“所有故障均在 600ms 内停稳”；发送调度、最后一帧时间、驱动器动作及实际制动时间都需要纳入测量。

### 4.2 不能把 6040=6 当成通用锁轴命令

6040=0x0006 属于撤销运行使能的处理，不是保持扭矩的锁轴命令。手册第 7.13 节还区分了快速停止、关机停止、禁止停止、暂停、报错停止的策略；bit8 暂停可保留使能，其动作受 605D 配置影响。

垂直轴应先明确正常停止、可处理异常、通信失效分别采用的停止和机械保持方案。不能把“速度清零后无条件撤使能”直接认定为防坠方案；已确认有机械支撑也不能替代不同位置和负载下的保持验收。

纯只读进程退出时，未经接管就向另一会话的驱动器写零速度或撤使能，也不应成为默认行为。

建议区分：

- 本会话已获得控制权或已尝试使能：即使软件 armed 尚未来得及置位，也必须进入相应清理。
- 纯只读且未接管：只关闭本进程资源。
- 检测到上次进程遗留使能：通过显式接管/恢复流程处理，禁止自动续跑旧目标。

控制权不能仅依据当前 armed 或门禁布尔值判断。使能中途失败、恢复流程和部分初始化都必须覆盖。

### 4.3 “每帧独立 try/except”可能仍发不出第二帧

当前 Windows 的 canopen.py 中，SDO 超时、abort 或错误回应会设置 poisoned；后续普通 SDO 请求会在发送前立即拒绝。

因此，如果 Jetson 新 failsafe_halt 使用现有普通 sdo.write，第一条 60FF 写入失败后，即使下一条 6040 有独立 try/except，也可能没有真正发送。

这属于需要用 Jetson 实际新增源码确认的条件性问题，尚不能断言新实现一定如此。验收应检查传输层真正发送的帧，而不是只检查“没有抛异常”。

必要时为失效会话提供受限、尽力发送的紧急路径，与正常 SDO 会话隔离；不得因此自动清除 poisoned、自动重连或把无回执发送宣称为停稳。

### 4.4 回下限位恢复仍绕过常规运动监督

Windows 当前 recover_to_lower_limit 位于 controller.py 第 384 行附近。本日上午日志没有说明修改此流程。

今日此前离线复现已确认：

| 前提 | 合理预期 | 当前 Windows 实现 |
|---|---|---|
| 底盘里程计缺失/过期 | 拒绝恢复运动 | 接受并下发非零速度 |
| 运动预算已耗尽 | 拒绝恢复运动 | 接受并下发非零速度 |

源码中，恢复使能并发出非零速度时仍没有建立 armed/busy/guard_active 的等价活动状态；没有调用常规底盘联锁、配置并监督节点保护或累计运动预算。持有控制锁的恢复循环主要只读限位，也需要检查是否使停止请求等待长事务结束。

另有一个明确的异常覆盖缺口：第 415 行附近已经写入 6040=0x000F，但 try/finally 到第 421 行附近才开始；中间状态等待或 6061 检查失败，可能跳过该 finally。由于控制器状态仍显示未使能，节点异常入口和 stop() 也可能据此不发送停止帧。应从首次可能改变驱动状态之前就建立异常覆盖与接管标志。

对应源码：[恢复与使能](../src/kinco_lift/controller.py)、[节点异常入口](../scripts/lift_node.py)、[SDO 会话与原始停车路径](../src/kinco_lift/canopen.py)。上述行号针对当前 Windows 副本，Jetson 新版需重新核对。

因此，新增退出兜底只覆盖了这个流程的一部分后果，不能替代恢复过程本身的监督。

建议让恢复成为受同等监督的明确状态：

- 入口确认真实底盘反馈、故障、限位、工作制预算及控制权。
- 使能前建立“可能已接管”的状态；使能与节点保护配置统一复用，避免复制出不完整路径。
- 运行期间持续检查底盘、故障、有效模式、方向/位置变化和节点保护，计入累计运动时间。
- 限制恢复总距离、时间与速度；允许及时取消或停止，避免整个循环长期独占控制锁。
- 每个失败阶段都撤销旧任务，并明确停止是否确认；需要重新建立会话参考才接受后续任务。
- 不屏蔽硬限位、不清编码器、不扩大正常行程来绕过恢复问题。
